PRACTICE CASE STUDY / BUSINESS & SYSTEMS ANALYSIS

From support requests to useful decisions.

A fictional help-desk scenario used to practice documenting stakeholder needs, defining a simple data model, and asking operational questions with SQL.

Portfolio transparency: This is a self-study demonstration produced with AI assistance. The company, support tickets, metrics, and data are fictional; it is not a description of paid employment or a deployed system.

01. The business problem

A small organization's IT team receives requests through email and chat. Without consistent categories, ownership, or priority criteria, requests may be overlooked and managers cannot identify recurring problems.

02. Stakeholders & questions

  • Employees: Can I report a problem and track its status?
  • Support staff: What must I work on next, and who owns each ticket?
  • IT manager: Which categories cause the largest backlog, and how long do tickets stay open?

04. Simplified data model

The sample separates employees from requests to avoid repeating employee names on every ticket. The SQL below is illustrative MySQL-style code; the repository includes a separate runnable SQL file with 12 fictional tickets.

CREATE TABLE employees (
  employee_id INT PRIMARY KEY,
  full_name VARCHAR(100) NOT NULL
);

CREATE TABLE tickets (
  ticket_id INT PRIMARY KEY,
  employee_id INT NOT NULL,
  category VARCHAR(40) NOT NULL,
  priority VARCHAR(12) NOT NULL,
  status VARCHAR(20) NOT NULL,
  created_at DATE NOT NULL,
  resolved_at DATE NULL,
  FOREIGN KEY (employee_id) REFERENCES employees(employee_id)
);

05. Questions the data can answer

Which categories account for the most unresolved work?

SELECT category, COUNT(*) AS open_count
FROM tickets
WHERE status <> 'Resolved'
GROUP BY category
ORDER BY open_count DESC;

How many open tickets are high priority?

SELECT COUNT(*) AS high_priority_open
FROM tickets
WHERE priority = 'High' AND status <> 'Resolved';

06. What I'd validate next

  • Agree on a consistent definition of priority with IT and business stakeholders.
  • Test the reporting rules against a larger, more representative sample.
  • Confirm whether a ticket may have multiple assignees or a history of status changes.
  • Add timestamps and a history table if service-level reporting is required.

07. What this practice demonstrates

The aim is to connect a user's problem to clear requirements, a workable structure, and testable questions. This is a starting point for building more independent analyst skills, rather than evidence of a finished production system.
